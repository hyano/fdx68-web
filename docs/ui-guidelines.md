# Web UI の実装方針

フロントエンドはビルド工程を持たない、素の HTML / CSS / JavaScript です。
Raspberry Pi に Node 環境を置かず、rsync でそのまま転送できるようにしています。

将来アイコン画像などで装飾する予定があるため、
**JavaScript のロジックを触らずに見た目を変えられる構造**を最初から作っています。

---

## 構成

```
frontend/
├── index.html          各行のマークアップを <template> として定義
├── css/
│   ├── tokens.css      色・余白・角丸・アイコンサイズ・フォントの CSS 変数
│   └── style.css       tokens.css の変数を参照する
├── js/
│   ├── app.js          初期化とイベント配線
│   ├── api.js          API 呼び出し
│   ├── ws.js           WebSocket 接続と再接続
│   ├── render.js       DOM の生成と更新
│   └── icons.js        種別 → アイコンの対応表（1 箇所だけ）
└── assets/
    ├── icons/          SVG スプライト
    ├── img/            背景・ロゴ等
    └── favicon.svg
```

---

## 3 つの原則

### 1. JS は見た目を決めない

JavaScript は**状態を `data-*` 属性とクラス名で出力するだけ**にします。
インライン style を JS から書かないでください。

```html
<li class="file-row" data-kind="fdx" data-mounted="0" data-protected="true">
<div class="drive-card" data-drive="0" data-state="inserted" data-seeking="true">
```

こうしておくと、「Drive 0 に挿入中のイメージだけ光らせる」
「2HD と 2DD でアイコンを変える」「シーク中にアクセス LED 風のアニメーションを出す」
といった装飾が、**CSS の追加だけ**で実現できます。

`[要変換]` バッジも `data-kind="convertible_image"` から
**CSS の `::after` で生成**します（JS がバッジ用の DOM を組み立てない）。

### 2. マークアップは `<template>` に置く

一覧の各行やドライブカードの HTML は `index.html` 内の `<template>` として定義し、
JS は `cloneNode` して値を埋めるだけにします。

装飾のために DOM 構造を変えたくなったとき、`index.html` の編集だけで完結します。

### 3. アイコンの参照は 1 箇所に閉じ込める

```js
// frontend/js/icons.js
export const ICONS = {
  directory: "📁",
  fdx: "💾",
  convertible_image: "💾",
  unsupported: "📄",
};
```

描画側は必ずこの対応表を経由します。
将来 SVG に差し替えるときは、**このファイルだけを変更**すれば全画面のアイコンが入れ替わります。

---

## アイコンの考え方

**FDX も `.d88` / `.xdf` も、どちらもフロッピーディスクイメージです。**
違いは「そのまま使えるか / 変換が必要か」という**状態**なので、
アイコンは同じにして `[要変換]` バッジで区別します。

```
📁 disk_set
💾 yamiketsu1.fdx
💾 original.d88   [要変換]
📄 readme.txt
```

アイコン列は「それが何であるか（種別）」を、バッジは「どういう状態か」を表す、
という役割分担を保ってください。

`💿` のような光学ディスクの絵文字は使いません。
実体は 5.25 インチのフロッピーディスクイメージであり、CD / DVD ではないためです。

### 将来 SVG に差し替えるときは

- **SVG スプライト方式**を使います。追加の HTTP リクエストが 1 本で済み（Pi 3A+ の
  非力な CPU に優しい）、`fill: currentColor` で CSS から色を制御でき、拡大しても劣化しません
- アイコンフォントや外部 CDN は使いません（LAN 内限定運用で外部依存を持たせないため）
- X68000 で使うのは **5.25 インチ 2HD** です。絵文字 `💾` が表す 3.5 インチとは
  形状が異なるので、5.25 インチのフロッピーを描いたアイコンにします
- FDX と変換可能イメージは同じ形状のまま、後者は彩度を落として「まだ使えない」ことを示します
- ディスク種別（2D / 2DD / 2HD）は `fdxtool` で取得できるため、
  `data-disk-type` として持たせられる構造にしてあります

---

## アセットの扱い

- 画像は `assets/` 配下に置き、**HTML / CSS / JS に base64 で埋め込まない**
  （差し替えが困難になるため）
- `assets/` は長めの `Cache-Control` で配信、HTML / JS は `no-cache`
- 装飾用アセットの合計は数百 KB 程度に抑える（Pi のメモリと LAN 帯域を圧迫しないため）

## Image Browser（ツリー）

macOS Finder のリスト表示のように、**その場で展開して下位が現れる**形式です。
ディレクトリを開いて降りる方式ではないため、「上位ディレクトリへ戻る」操作はありません。

### 遅延読み込み

ノードを開いたときに `GET /api/images?path=...` をそのディレクトリに対して呼びます。
全階層を一度に読むと、Pi 3A+ ではイメージが増えるほど初回表示が重くなるためです。

### 展開状態を保持する

ファイル操作（アップロード・変換・削除・リネーム・新規作成）の後は、
**影響を受けたノードだけを再取得**し、ツリー全体を作り直しません。

開いていた枝が勝手に閉じると、複数枚組ソフトのフォルダを行き来する作業が中断されます。

展開状態は `localStorage` に保存し、再読み込み後も同じ枝が開いた状態で復帰します。

### 並び順

**ディレクトリ優先 + 自然順ソート**です。

`disk1, disk2, disk10` が辞書順で `disk1, disk10, disk2` にならないようにします。
X68000 のソフトは複数枚組でこの命名が頻出するため、
間違えると実用上かなり不便になります。

列ヘッダのクリックでサイズ・更新日時のソートにも切り替えられます。

### 更新日時の表示

API は **ISO8601 の UTC** で返し、表示はブラウザのローカル時刻に任せます。
Pi 側のタイムゾーン設定に表示が左右されないようにするためです。

## 表示は常に古くなりうる前提で作る

イメージディレクトリは Web UI 以外からも変更されます
（macOS からの `rsync`、SSH での `fdxconv` 手動実行、別のブラウザタブや端末からの操作）。

4 段構えで追随します。

1. **手動リロード** … ツールバーの `[⟳ 更新]`。展開中のノードだけを再取得し、
   展開状態とスクロール位置を保つ
2. **展開時は必ず再取得** … キャッシュがあってもまず即座に描画し、裏で取り直して
   差分があれば更新する（stale-while-revalidate）。
   「折りたたんで開き直せば最新になる」という直感どおりの挙動にする
3. **ウィンドウ復帰時の自動更新** … `visibilitychange` を契機に展開ノードを再取得。
   「macOS から rsync してブラウザに戻る」という頻発する操作で明示的な更新を不要にする
4. **WebSocket 通知** … 自分たちの API 経由の変更は `images_changed` で
   他のクライアントに通知する

**ツリー全体をサーバー側で定期スキャンする方式は採りません。**
SD カードを毎秒走査すると fddemu のリアルタイム動作に影響しうるうえ、
イメージが増えるほど無駄が大きくなるためです。

### 古い状態での操作は正常系

外部で消されたファイルに対して挿入や削除を実行する事態は普通に起こります。

すべての操作は「対象が既にない / 既に存在する」場合に分かりやすいエラーを返し、
**UI 側は該当ノードを自動で再取得して表示を実態に合わせます**
（「ファイルが存在しません。一覧を更新しました。」）。

ノードの再取得が 404 になった場合は、エラーを出して固まるのではなく、
そのノードをツリーから取り除きます。

## ドラッグ＆ドロップ

**外部からのアップロードと、ツリー内部の移動を確実に区別します。**

内部ドラッグでは `dataTransfer.setData("application/x-fdx68-paths", ...)` に
独自 MIME タイプでパスを載せます。`drop` 時に `dataTransfer.types` が
`Files` を含むならアップロード、独自タイプならば移動として扱います。

ここを曖昧にすると、OS からのファイル投下を移動と誤認して失敗します。

- 投入先となるフォルダ行を **1 つだけ**ハイライトする
  （どこに入るのか分からないまま数 MB を転送させないため）
- ブラウザ既定のファイルを開く挙動を抑止するため `dragover` / `drop` で
  `preventDefault()` する
- Option (Alt) を押しながらのドロップはコピー。`dropEffect` を切り替えて
  カーソル表示も変える
- アップロードの進捗は `fetch` では取れないため `XMLHttpRequest` の
  `upload.onprogress` を使う
- **複数ファイルは並行させず 1 つずつ順に送る**（Pi 3A+ の CPU と
  SD カード I/O を飽和させないため）

## 確認ダイアログ

以下は必ず確認を取ります。

- ファイル・フォルダの削除（**件数を明示する**）
- Raspberry Pi の再起動
- Raspberry Pi のシャットダウン（「シャットダウン後は Web UI にアクセスできなくなります」）

## 注意表示

X68000 がディスクにアクセス中かどうかは `fddctl` から直接取得できませんが、
**シリンダ位置（CL）の変化はヘッドシークの痕跡**です。

直近 N 秒以内に CL が変化したドライブには、UI 上で注意表示を出します。
ハード的な保証ではないヒント表示として扱ってください。

以下の操作で表示します。

- ディスクの挿入・排出（アクセス中の交換は危険）
- アップロード（SD カードへの書き込みが fddemu に影響しうる）
- 挿入中イメージの複製（書き込み中だと不整合なコピーになりうる）

## ライトプロテクトは 2 種類ある

混同させないように、UI 上で明確に分けます。

| | 場所 | 永続性 |
|---|---|---|
| `fddctl -c protect` | Drive セクションの「Write Protect」 | fddemu を止めれば消える |
| `fdxtool -s -p on` | ファイルの「ディスク属性編集」 | FDX ファイルに永続する |

ディスク属性編集のダイアログには
「これは FDX ファイル自体の属性です（ドライブの実行時プロテクトとは別）」と注記します。

---

## アクセシビリティ

- ツリーには `role="tree"` / `role="treeitem"` / `aria-expanded` を付ける
- 上下キーで移動、左右キーで開閉できるようにする
- ドラッグ＆ドロップが使えない環境のため、ツールバーにファイル選択ボタンを併設する
