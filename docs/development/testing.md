# テスト方針

テストを 3 段階に分けます。

| 段階 | 実行環境 | 自動化 |
|---|---|---|
| Unit Test | macOS / CI | 自動 |
| Integration Test | macOS / CI（Mock バックエンド） | 自動 |
| Hardware Integration Test | Raspberry Pi + X68000 実機 | 手動チェックリスト |

```bash
./scripts/test.sh    # Unit → Integration → ruff → shellcheck → dry-run
```

いずれかが失敗した時点で非ゼロ終了し、`deploy.sh` はデプロイを中止します。

---

## Unit Test（`tests/unit/`）

外部プロセスもファイルシステムもほとんど使わない、純粋なロジックのテストです。

### `fddctl -l` のパーサー

実機の出力形式をそのまま入力として与えます。

- 通常の 2 ドライブ分の出力
- `EMPTY`（未挿入）の判定
- `ON` / `--`（ライトプロテクト）の判定
- **パスに空白を含む場合**（`split("|", 3)` で 4 要素目を分割しないこと）
- **日本語を含むパス**
- **拡張子が `.FDX` と大文字の場合**
- `Error : Can't connect to emulator process` の検出
- シリンダ値が数値として解釈できない場合のフォールバック

### `fdxtool` の情報出力パーサー

- 正常な出力からディスク名・種別・RPM・シリンダ数を取り出せること
- **パースに失敗しても生の出力を保持すること**
  （FDX68 のバージョン差で書式が変わっても情報が失われないようにするため）

### パス検証

イメージルートからの脱出を試みる入力をすべて拒否します。

- `../` を含むパス
- 絶対パス（`/etc/passwd`）
- `~` を含むパス
- **ルート外を指すシンボリックリンク経由の脱出**
- ルート自身（`""` や `"."`）は許可されること

### 名前の検証

- `/` `\` NUL・制御文字を含む名前の拒否
- `.` `..` そのものの拒否
- 空文字・空白のみの拒否
- 先頭・末尾に空白またはドットを持つ名前の拒否
- **日本語の名前が許可されること**（X68000 のソフト名を日本語で管理するため）
- 255 バイトを超える名前の拒否

### その他

- 拡張子によるファイル種別判定（大文字小文字を区別しないこと）
- 変換先パスの生成（`disk.d88` → `disk.fdx`）
- 新規イメージ作成時の `.fdx` 自動付与
- 複製時の連番生成（`disk copy.fdx` → `disk copy 2.fdx`）
- コマンド引数の組み立て
- 状態の差分検出（変化がないときに通知しないこと）
- **一覧の並び順** … ディレクトリ優先、自然順ソートで `disk1 < disk2 < disk10` となること

自然順ソートを検証するのは、X68000 のソフトが複数枚組で
`disk1` `disk2` … `disk10` という命名を多用するためです。
辞書順だと `disk1, disk10, disk2` になり、実用上かなり不便になります。

## Integration Test（`tests/integration/`）

FastAPI アプリケーション全体を Mock バックエンドで動かします。
`httpx` の ASGI トランスポートを使い、実際にサーバを起動せずにリクエストを送ります。

### API の正常系

全エンドポイントについて、期待するステータスコードとレスポンス形式を確認します。

### ガード条件（重要）

ディスクイメージを壊す事故を防ぐためのものなので、重点的にテストします。

- 挿入中のイメージの**削除**が拒否されること
- 挿入中のイメージの**リネーム**が拒否されること
- 挿入中のイメージの**移動**が拒否されること
- 挿入中のイメージの**ディスク属性編集**が拒否されること
- **挿入中のイメージを含むディレクトリ**のリネーム・移動が拒否されること
- **フォルダを自分自身、または自分の子孫へ移動**しようとした場合に拒否されること
- 変換先・作成先・リネーム先・移動先に既存ファイルがある場合に 409 が返ること
- 同一ディレクトリへの移動が、何もせず成功として返ること

### パスの検証

- ルート外へのアクセスが 400 / 403 で拒否されること

### アップロード

- 正常系（複数ファイル）
- **`../evil.fdx` や `sub/dir/x.fdx` のような相対パス付きファイル名が
  ベース名に切り詰められること**
  （ブラウザからのフォルダドロップで実際にこの形式のファイル名が来ます）
- 対応していない拡張子の拒否
- サイズ上限を超えた場合に中断し、**`.part` ファイルが残らないこと**
- 同名ファイルが既にある場合の 409
- 自動変換: 元ファイルと FDX の両方が残ること、変換先の FDX が既にあれば
  （拡張子の大文字小文字違いや同一リクエスト内の衝突を含む）上書きせず元ファイルだけを保存すること

### 複製

- 連番付きの名前が生成されること
- 失敗時に `.part` が残らないこと

### ダウンロード

- **日本語ファイル名が `filename*=UTF-8''` で正しく符号化されること**
  （`filename=` だけでは文字化けします）

### 一括操作

- 一部が失敗しても残りが処理されること
- 失敗した項目が理由付きで報告されること

10 件選んで 1 件が挿入中だったときに 9 件が処理されないのは不便なので、
「途中で止めない」ことを明示的にテストします。

### WebSocket

- 新規接続時に現在の状態が即座に 1 回送られること
- 状態が変化したときだけ通知されること（変化がないときに送らないこと）
- ファイル操作の成功時に `images_changed` が正しいパスで送られること

### 外部変更への追随

- 外部で削除されたファイルへの操作が、明確なエラーになること

## インストーラのテスト

```bash
shellcheck scripts/*.sh scripts/ci/*.sh
./scripts/install.sh --dry-run
```

`--dry-run` は実行計画を表示するだけで、何も変更しません。
どちらも `./scripts/test.sh` に含まれているため、通常は個別に実行する必要はありません。

ローカルで実行するのは dry-run までです。実際のインストールは `/etc` と systemd を触るため、
開発ホストでは走らせません（macOS では実機コマンドを実行しない、という前提もあります）。

### CI での実インストール

dry-run は分岐が壊れていないことしか見ません。`run()` の中身（venv 作成・pip・sudoers 設置・
systemd 起動・疎通確認）とダウンロード経路は一度も実行されないため、
systemd unit や sudoers のテンプレートを壊しても dry-run は通ってしまいます。

そこで CI では、**FDX68 コマンドのスタブを生成して `install.sh` を非 dry-run で最後まで実行**します。
スタブは `scripts/ci/make-fdx68-stub.sh` が生成します（CI 専用。実機では絶対に使いません）。
FDX68 本体は再配布できないため CI に置けませんが、検証したいのは `install.sh` とパッケージングであって
FDX68 そのものではないので、これで目的を達成できます。

| ジョブ | ランナー | 検証する範囲 |
|---|---|---|
| `install` | `ubuntu-latest`（x86_64） | FDX68 が導入済みの状態からの経路。venv・`.env` 生成・sudoers・systemd・疎通確認・再実行・`--uninstall` |
| `install-arm` | `ubuntu-24.04-arm` | 上に加えて FDX68 の取得経路。`--fdx68-url` → SHA256 照合 → 展開 → ELF アーキテクチャ検証 → 配置 |

`install-arm` は実機と同じ `aarch64` として判定されるため、アーキテクチャ判定と
ダウンロード物の ELF 検証が実際に効きます。ダウンロード元にはスタブから作った tarball を
`file://` で渡すので、retropc.net には一切アクセスしません。
SHA256 が一致しないときに中止することも、わざと誤った値を渡して確認しています。

**CI が緑でも FDX68 本体そのものは検証していません。** スタブはそれらしい出力を返すだけで、
GPIO も FDD 信号も扱いません。

x86_64 では FDX68 が配布されていないため、対象外のアーキテクチャでは dry-run に限り
警告を出して導入手順を飛ばします（実際の導入では従来どおりエラーで中止します）。
開発ホストが Apple Silicon の場合は `arm64` と判定されて実機と同じ経路を通るので、
x86_64 側の経路は CI でのみ検証されます。

### 実機での確認

**既存の Raspberry Pi で 2 回連続実行し、2 回目が何も壊さないこと（冪等性）**を確認します。
特に `.env` とイメージディレクトリの中身が変化しないことが重要です。

ただし、これでは**真に素の環境での検証にはなりません**。
クリーンな環境での確認には予備の SD カードが必要です。
手順は [installation.md](../guide/installation.md) の手動チェックリストに記載しています。

## CI（GitHub Actions）

実機なしで回せる範囲を `ubuntu-latest` 上で検証します。

- ruff（lint / format check）
- pytest（Unit + Integration、`FDX68_BACKEND=mock`）
- shellcheck（`scripts/*.sh` / `scripts/ci/*.sh`）
- `install.sh --dry-run`
- **FDX68 のスタブを使った実インストール**（x86_64 と aarch64。前節を参照）
- **Python 3.11 と 3.13 のマトリクス**（Bookworm / Trixie 相当）

3.11 を含めるのは、Bookworm で動かない構文を使ってしまう事故を防ぐためです。

別途、**配布 URL の死活監視**を週次ジョブで行います（`curl -I` で HTTP 200 を確認するだけ）。
FDX68 の配布 URL の構成が変わった場合に気付けるようにするためです。
